# MConnect Protocol v3.1 Migration Guide

> **Status**: Phase 0A1 in-progress. Capability negotiation + `local_pairing_auth` types landed in `packages/shared/src/protocol/messages.ts`. Server reject-handler + CLI auth-bridge follow in Phase 0A1 continuation. CLI bumped from `2.0` → `3.0` in `packages/cli/src/ws/protocol.ts`.

This document describes the v3.1 capability negotiation layer, the new `local_pairing_auth` message family, and the v2 → v3 auth migration path for the MConnect WebSocket protocol.

Source of truth for the message types: `packages/shared/src/protocol/messages.ts`. Source of truth for v3.0 baseline: `docs/protocol/v3.md`.

---

## Capability matrix

v3.1 introduces explicit capability negotiation. Every client advertises a capability set on its first `auth` (or `local_pairing_auth`) message via the new optional `clientCapabilities?: string[]` field. The server responds with `serverCapabilities?: string[]` on `auth_success` containing the **intersection** (unioned then filtered to what server actually supports). Unknown capabilities to either side trigger a typed `unsupported_capability` server message rather than a silent drop.

| Capability id              | Owner   | Phase | Description                                                                 |
|----------------------------|---------|-------|-----------------------------------------------------------------------------|
| `desktop:session_list`     | desktop | 1     | Desktop client may request `desktop:session_list` enumeration of sessions   |
| `desktop:fork`             | desktop | 3     | Desktop client may request fork of a session at a specific message id       |
| `desktop:resume`           | desktop | 3     | Desktop client may request resume from a forked branch                      |
| `worktree:lifecycle`       | worktree| 3     | Client may request worktree create/cleanup operations per agent             |
| `local_pairing_auth`       | cli     | 0A1   | Client may authenticate via local pairing token (CLI direct attach only)    |
| `client_capabilities`      | shared  | 0A1   | Client supports the capability negotiation field on auth                    |
| `unsupported_capability`   | shared  | 0A1   | Client supports the typed `unsupported_capability` server message           |

Capability ids use the form `<namespace>:<feature>`. The `<namespace>` segment maps to a logical subsystem (`desktop`, `worktree`, `cli`, `mcp`, ...). The `<feature>` segment is opaque to the negotiation layer; semantics are defined per message family.

## Required for v0.2.0

For a v0.2.0 desktop client to function end-to-end, both client and server MUST advertise (and the union MUST contain) the following capabilities:

- `client_capabilities` — gates everything below
- `unsupported_capability` — required so the desktop knows when to fall back gracefully
- `desktop:session_list` — required for the sidebar to populate
- `worktree:lifecycle` — required for orchestrator-style multi-agent isolation

For the fork-and-resume features shipping in Phase 3:

- `desktop:fork`
- `desktop:resume`

Clients that do not advertise these capabilities continue to work in v3.0 mode; the desktop simply hides the v3.1-only UI affordances.

## Backward-compatible

The following changes are strictly additive and do not break v0.1.10 npm-published CLI clients or v3.0 iOS clients on TestFlight:

- `clientCapabilities?: string[]` on `AuthMessage` — optional; absent means "v3.0 client, no v3.1 features advertised".
- `serverCapabilities?: string[]` on `AuthSuccessMessage` — optional; absent means "v3.0 server".
- New message type `local_pairing_auth` — never emitted by v0.1.10 clients; absence does not change v3.0 auth flow.
- New message type `unsupported_capability` — only emitted in response to v3.1 traffic that the receiving end cannot honor.

Legacy clients (v0.1.10 npm CLI) continue to authenticate via the existing v2 query-param `?token=&v=` flow at `packages/cli/src/ws/ws-hub.ts:241-275`. The CLI auth-bridge (Phase 0A1 continuation, file `packages/cli/src/ws/auth-bridge.ts`) accepts both v2 query-token and v3.1 first-message `local_pairing_auth`, dispatching to the existing pairing-token validator in `packages/cli/src/security.ts`.

## Hard errors

The following are **hard errors** in v3.1 — the server MUST close the connection with an explicit error message rather than silently dropping or logging:

| Trigger                                                              | Server response                                                                                       |
|----------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------|
| Client sends `local_pairing_auth` to the **Bun server** (`packages/server`) | `unsupported_capability { capability: 'local_pairing_auth', reason: 'JWT-only endpoint' }` then close |
| Client sends a message family not in the negotiated `serverCapabilities` set | `unsupported_capability { capability: '<family>', requestedMessageType: '<msg.type>' }`               |
| Client sends `auth` with `clientCapabilities` containing a malformed id (not `<ns>:<feat>`) | `auth_failed { reason: 'invalid_token', retryable: false }` (treat as protocol violation)             |
| Client sends an unknown top-level `type` after a successful `auth`   | `unsupported_capability { capability: 'unknown_message_type', requestedMessageType: '<msg.type>' }`   |

The previous behavior at `packages/cli/src/ws/ws-hub.ts:524-525` (`console.warn('[WSHub] Unknown message type:', ...)`) is upgraded to send a typed `unsupported_capability` message back to the client in addition to the warn.

## Auth migration

There are now **two parallel auth paths**, segregated by endpoint:

### Path A — Bun server (`packages/server`), JWT only

- Client sends `auth { token: <JWT>, protocolVersion: '3.0' | '3.1', clientType, clientCapabilities? }`.
- Server validates JWT via the existing `jose`-based validator in `packages/server/src/auth/`.
- Server responds with `auth_success { ..., serverCapabilities }`.
- **Server REJECTS `local_pairing_auth`** with `unsupported_capability { capability: 'local_pairing_auth', reason: 'JWT-only endpoint' }`. This is enforced by a regression test at `packages/server/__tests__/protocol/reject-local-pairing-auth.test.ts` (Phase 0A1 continuation deliverable).

### Path B — CLI direct attach (`packages/cli`), local pairing token

- Client sends `local_pairing_auth { pairingToken, protocolVersion: '3.1', clientType, clientCapabilities? }`.
- CLI validates `pairingToken` against its local registry in `packages/cli/src/security.ts`.
- CLI responds with `auth_success { ..., serverCapabilities }`.
- CLI MUST NOT import `jose` or any JWT validator. JWT remains server-only. This is enforced by a regression check: `! grep -q "from 'jose'" packages/cli/src/ws/auth-bridge.ts`.
- The CLI auth-bridge ALSO continues to accept the legacy v2 query-param `?token=&v=` flow for v0.1.10 npm-published clients (Exception A from the v0.2.0 plan §1 principle 1).

### Sunset timeline

- **v0.2.0 (Phase 0A1)**: Both v2 query-token and v3.1 `local_pairing_auth` accepted on the CLI WebSocket. iOS keeps using `auth` (JWT) when connecting to the Bun server, and switches to `local_pairing_auth` only when pairing directly via QR.
- **v0.3.x**: v2 query-token deprecated in CLI logs (still works; emits warning).
- **v0.4.x or later**: v2 query-token removed. `local_pairing_auth` becomes the only direct-attach auth path on the CLI.

The CLI version published on npm (`lecoder-mconnect@0.1.10` at the time of this document) and any iOS TestFlight build that pre-dates v3.1 will continue to work through v0.3.x without code changes.
